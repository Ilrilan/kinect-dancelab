# DanceLab

Личный проект: танцевальная игра-оболочка на ПК с проектором и сенсором глубины.
Цель — не развлечение, а **отработка хореографии и пластики тела** с измеримой
обратной связью.

Агент проекта: ZCode (с 2026-11-21, до этого Claude Code). Этот файл — вход для
агента. База знаний и память проекта: `knowledge/` (Zettelkasten, под гитом;
владелец переносит проект между устройствами клона репо, агент обязан
подхватить всё сразу после клона). В начале сессии читать `knowledge/INDEX.md`,
`knowledge/status/STATUS.md` и общие правила
`knowledge/zettel/general-working-rules.md`.

Разработка ведётся **spec-driven**. Владелец проекта пишет контракты, требования
и сценарии; код пишут агенты по спеке. Правило:

> Нет сценария — нет кода. Нет фикстуры — нет сценария.

## Как работать в этом репозитории

1. Спека в `specs/` источник истины (корень `specs/system.md`, схема переноса в таблице Drill-down).
   В `spec/` остались только не перенесённые файлы: `00-overview.md` (не-цели) и
   `70-manual-tuning.md` (перцептивные параметры). Остальное перенесено в `specs/` и удалено.
   Код обязан спеке соответствовать, а не наоборот.
2. Контракты задаются **схемами** (JSON Schema, сигнатуры интерфейсов), не прозой.
3. Перцептивные параметры живут в `spec/70-manual-tuning.md` до тех пор, пока
   владелец не натанцует их значения. После этого параметр переезжает в контракт
   вместе с найденным числом.
4. Метрика сравнения специфицируется **инвариантами**, не ожидаемыми значениями
   (`specs/core/scoring.md`). Фикстуры для инвариантов генерируются из эталона
   программно — танцевать для их проверки не нужно.
5. Всё, что зависит от профиля пользователя, идёт в производный кеш, а не в
   общий бандл трека.
6. Задел на будущее: не расширять формат и архитектуру заранее, если это
   дорого. Но то, что уже оценивалось и вероятно (например, сцена со списком
   сенсоров под многосенсорную конфигурацию), предусматривать сразу: это
   дешевле, чем потом перекраивать кодовую базу. Критерий: цена задела сейчас
   против цены переделки потом, и вероятность того, что он понадобится.
7. Single Source of Truth: каждое знание живёт в одном месте. При переносе
   документа прежний полностью удаляется или остаётся краткой
   ссылкой-референсом на новый; параллельные копии не ведутся (правило
   владельца 2026-11-21).

## Структура репозитория

```
AGENTS.md          этот файл — вход для агента
CLAUDE.md          краткая ссылка на AGENTS.md (для инструментов до ZCode)
specs/             спека, источник истины (system, core, player, studio, capture, hardware, datasets, decisions, estimates)
spec/              остаток старой спеки
  00-overview      задача, объём, не-цели
  70-manual-tuning перцептивные параметры, пока не натанцованы
.agents/skills/    скиллы агента: sdd, subagent-delegation
.zcode/agents/     определения ролей-сабагентов
knowledge/         база знаний (Zettelkasten): zettel/, reference/, status/
```

Код слоя захвата уже есть (спек specs/capture/index.md): решение DanceLab.sln,
src/DanceLab.Capture (общая библиотека), src/DanceLab.Capture.Kinect и
src/DanceLab.Capture.Nuitrack (реализации под трекерами), tools/sensor_probe
(консоль и сценарий записей), tools/capture_report (сводка по записям, Node TS), tools/sensor_view (WPF, живой просмотр и воспроизведение записей),
tests/DanceLab.Capture.Tests. Сборка: dotnet build DanceLab.sln, тесты: dotnet test
tests/DanceLab.Capture.Tests и tests/DanceLab.Core.Tests (достройка суставов, src/DanceLab.Core). Скрипты на Node TS: npm run check (типы, линтер, prettier, тесты).
src/DanceLab.Core реализует достройку суставов: PoseReconstructor, Conversion.
Инструменты датасета: tools/aist_download (Node TS), tools/aist_import (Python,
SMPL и канонические позы), tools/finedance, tools/pose_eval (измерения порогов
дрожания и длины кости). Studio и Player ещё не начаты; когда появятся,
раскладка следует Д4 (Studio и Player — разные приложения) и Д5 (одно
WPF-приложение на C#, без вебвью):

```
src/DanceLab.Studio/    WPF, офлайн: импорт, разметка, отчёты
src/DanceLab.Player/    WPF, живой режим
tools/aist_import/      Python: импортёр AIST++ → канонические позы
```

Датасеты, бандлы, записи сессий и SQLite-кеш в репозиторий не попадают —
см. не-цели в `spec/00-overview.md` и `.gitignore`.

## Ролевая модель (с 2026-11-21)

Главное окно ведёт ПМ на основной модели: диалог с владельцем, спеки и
контракты (шаги 1-5 SDD), резка подтверждённого контракта на задачи, глубокое
ревью диффа с чек-листом, приёмка, коммиты и push. Синтез текстов не
делегируется.

Сабагенты (`.zcode/agents/`, модель GLM-5.3-Flash; проверено тест-спавном
2026-11-21):

- implementer: код и тесты одной задачи по контракту, прогон сборки и тестов;
- critic: второй контур ревью, проверяет пункты чек-листа ПМ по коду и
  независимым прогоном проверок;
- designer: визуальная приёмка UI (sensor_view): скриншоты и вердикты по
  критериям спеки;
- explorer: сбор фактов (таблицы API, инвентаризация, где что лежит), read-only.

Брифы, бюджеты и контроль дрейфа: скилл subagent-delegation (`.agents/skills/`).

## База знаний и статусы

- Долговременная память: `knowledge/` (Zettelkasten). Атомарные заметки в
  `knowledge/zettel/` с `[[связями]]`, карта в `knowledge/INDEX.md`, справочные
  массивы в `knowledge/reference/`. Одна заметка = одна тема; INDEX пополняется
  в том же изменении.
- Операционный снимок: `knowledge/status/STATUS.md`, обновляется после каждого
  шага. Закрытая задача → коммит сразу.
- Исполнители ведут файл статуса задачи из брифа (`knowledge/status/reports/`)
  и дополняют его не реже каждых 10 минут. Длительные задачи запускаются фоном.
  ПМ при наличии активных задач каждые 10-15 минут проверяет статусы
  исполнителей и фиксирует их коммитом: скачок напряжения или перезагрузка не
  должны терять значимую часть работы.

## Общие правила работы

Единый источник: `knowledge/zettel/general-working-rules.md` — темп и
чекпойнты, границы инициативы, делегирование, стиль текстов, верификация и
скрипты, окружение, размещение файлов, Single Source of Truth. Обязательны к
исполнению; дубль в этом файле не ведётся.

## Чего в этом проекте НЕ делаем

Список не-целей в `spec/00-overview.md`. Коротко: не поддерживаем другие сенсоры,
не строим модель сложности треков, не распознаём людей, не детектируем контакт,
не заводим базу данных как источник истины, не тащим датасеты в репозиторий.
