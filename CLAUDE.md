# DanceLab

Личный проект: танцевальная игра-оболочка на ПК с проектором и сенсором глубины.
Цель — не развлечение, а **отработка хореографии и пластики тела** с измеримой
обратной связью.

Разработка ведётся **spec-driven**. Владелец проекта пишет контракты, требования
и сценарии; код пишут агенты по спеке. Правило:

> Нет сценария — нет кода. Нет фикстуры — нет сценария.

## Как работать в этом репозитории

1. Спека в `spec/` — источник истины. Код обязан ей соответствовать, а не наоборот.
2. Контракты задаются **схемами** (JSON Schema, сигнатуры интерфейсов), не прозой.
3. Перцептивные параметры живут в `spec/70-manual-tuning.md` до тех пор, пока
   владелец не натанцует их значения. После этого параметр переезжает в контракт
   вместе с найденным числом.
4. Метрика сравнения специфицируется **инвариантами**, не ожидаемыми значениями
   (`spec/50-scoring.md`). Фикстуры для инвариантов генерируются из эталона
   программно — танцевать для их проверки не нужно.
5. Всё, что зависит от профиля пользователя, идёт в производный кеш, а не в
   общий бандл трека.

## Структура репозитория

```
CLAUDE.md          этот файл — вход для агента
spec/              спека, источник истины
  00-overview      задача, объём, не-цели
  10-canonical-pose  каноническая поза (топология Kinect v2)
  20-data-model    модель данных и бандл трека
  30-studio        офлайн-приложение: импорт и разметка
  40-player        живой режим: бюджет задержки
  50-scoring       метрика сравнения, инварианты
  60-ui            экраны и обратная связь
  70-manual-tuning перцептивные параметры, пока не натанцованы
  80-hardware      сенсор, зона, арифметика точности
  85-datasets      AIST++ и прочие источники эталонов
  90-decisions     журнал решений и открытые вопросы
```

Кода пока нет. Когда появится, раскладка следует Д4 (Studio и Player — разные
приложения) и Д5 (одно WPF-приложение на C#, без вебвью):

```
src/DanceLab.Studio/    WPF, офлайн: импорт, разметка, отчёты
src/DanceLab.Player/    WPF, живой режим
src/DanceLab.Core/      формат бандла, каноническая поза, скоринг
tools/aist_import/      Python: импортёр AIST++ → канонические позы
```

Датасеты, бандлы, записи сессий и SQLite-кеш в репозиторий не попадают —
см. не-цели в `spec/00-overview.md` и `.gitignore`.

## Порядок первых работ

1. `spec/10-canonical-pose.md` и `spec/20-data-model.md` довести до схем.
2. Питоновский импортёр AIST++ → канонические позы + битовая сетка.
3. Инварианты скоринга и генератор фикстур (`spec/50-scoring.md`).
4. Нарезка на движения, автоматическая.
5. Отрисовка призрака палками, камера как параметр.
6. Слой захвата — последним, когда приедет сенсор.

Обоснование порядка: слой захвата это одна реализация интерфейса `PoseSource`,
а первые две (из датасета и из записи) нужны раньше и железа не требуют.

## Общие правила работы

Общие для всех проектов владельца. Копия лежит в памяти агента
(`general-working-rules`); при правке менять обе.

### Темп и чекпойнты

- Не более 5 минут работы без фиксации в файл: результат этапа сразу в статус, журнал или память.
- Рабочая итерация 20-40 минут, затем: журнал, память, сброс контекста.
- STATUS/HANDOFF актуальны всегда: сессии рвутся, обновлять после каждого шага. Закрыл задачу → коммит сразу.
- Работать открыто: план «сейчас/дальше» до команд, статус текстом, не исчезать в bash.
- При словах «сброшу контекст»: выдать готовый промт восстановления сессии после /clear.

### Границы инициативы

- Вопросы закрывает владелец. Перед записью «закрыто» тест: появилось правило, которое можно вписать в документ? Нет → вопрос открыт, даже если владелец писал по теме.
- Правка формулировки, исправление описания, указание на ошибку ≠ ответ на вопрос. В статус пишется дословная цитата ответа, не слово «закрыт».
- Уточнение по тексту = дополнение к одобренному, не замена. Замена блока согласуется: перечислить, что уйдёт, и спросить. Файлы проекта не трогать до подтверждения по каждому пункту.
- Не ресёрчить лишнего: готовый паттерн в контексте применяется сразу; сначала README пакета, потом grep по .d.ts.
- perf-анализ: только планирование, фиксы по явному запросу.
- Ревью жёсткое состязательное, без приглаживания. Integrity: красная линия, защитные дисклеймеры и нейрослоп убираются.

### Делегирование

- Сабагенты только через скилл `subagent-delegation` (`.claude/skills/`): точные пути в брифе, бюджет, замороженный вход, чекпойнт до первого чтения. «Не подтвердил» = не подтверждено. Дрейф агента → остановить и делать самому.
- Полный обход документов при обновлении скиллов: спавнить агента на весь корпус, не выборочно.

### Стиль текстов

Относится к любым текстам, которые агент пишет для владельца и от его имени: спеки, документация, коммиты, отчёты, ответы в чате, заявки, PDR, вики, деки.

- Без жирного. Заголовки секций: plain text с точкой («Роль.»).
- Без длинных тире. Там где тире играло роль запятой: «:», «.», «,» или переписать предложение.
- Пустая строка перед каждым списком и таблицей, включая вложенные под-списки: иначе Confluence схлопывает в одну строку.
- Стрелки (→) только как техническая нотация (938k→42k, статусы Jira). Причинность в прозе: «так как», «потому что», «следовательно».
- Короткие предложения, одна мысль на предложение. Абзац с тремя и более однородными элементами → вложенные списки.
- Русский. Профессиональные термины, имена, код не переводить: XaaS, semver, CI, OKR, KR, RFC, TL;DR, hands-on, span. Разговорный англ-жаргон с русским эквивалентом заменить русским.
- Устная реплика ≠ текст деливерабла: смысл переносить, формулировку переписывать в докладный регистр. Дословно только по явной диктовке.
- Подлежащее живое: «я», «мы», «команда», не «масштабирование» и «делегирование».
- Запрещённые обороты: леверидж, people-сигналы/people-радар, by construction, outcome-gated, toil, мета-скобки «(ключевой аргумент)», «Связующая нить:», «X не Y» защитные дисклеймеры, блоки «Честно:».
- PDR/Минто: один статус на головном уровне, корень не симптомы, термины ролей, читатель укладывается в 20 минут.

### Верификация и скрипты

- Каждое нетривиальное изменение с тестом. Полный прогон после правок: типы + тесты + линт + prettier, все четыре.
- Скрипты, пробы, разбор логов: только Node TS через ts-node/tsx. Python и sh-логика не используются. Исключение: необходимый минимум на Python там, где используются чужие готовые внешние инструменты. В DanceLab это весь импортёр `tools/aist_import/` целиком (SMPL, librosa, преобразование в каноническую позу, а также подгонка SMPL по ключевым точкам, где она нужна), отдельную границу внутри него не вводим. Всё остальное, что агент пишет с нуля, только Node TS. Python где-либо ещё только при объективной и сильной причине и только после обсуждения и разрешения владельца; молча не добавлять.
- Не дублировать механизмы: модифицировать существующий стор, транспорт, атом; параллельный не создавать.
- SDD: код только после подтверждения контракта; статусы draft/scenarios/realisation/done; Tasks-секции при переходе в `done` удаляются (история в git); docs = статичный снимок.

### Окружение

- Массовые поиски: grep -r по нескольким репо висит. Только Node-скрипты одного прохода.
- Мобильный вид: только device mode (devices['iPhone 13']), не голый setViewport.

### Размещение файлов

- Документация и планы: в репе под гитом (docs/, docs/instructions/), не в ~/.claude/plans/.

## Чего в этом проекте НЕ делаем

Список не-целей в `spec/00-overview.md`. Коротко: не поддерживаем другие сенсоры,
не строим модель сложности треков, не распознаём людей, не детектируем контакт,
не заводим базу данных как источник истины, не тащим датасеты в репозиторий.
