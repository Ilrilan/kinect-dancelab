# Player: пробный плеер (trial)

> Status: realisation
> Parent: [index.md](index.md)
> Источник: задача владельца 2026-11-21: «сделать пробную версию плеера, в которой уже можно будет отрабатывать движение по эталону… любое из простых в датасете, плеер в окне с записью и музыкой, параллельно движется эталон-призрак, рядом мой призрак с оценкой успешности движения приблизительной».
> Автономный режим: переходы сценарии→контракт и контракт→realisation сделаны агентом по распоряжению владельца 2026-11-21 («дальше едешь автономно до моего следующего сообщения»), подтверждение постфактум. Эталонная последовательность выбрана агентом: Lock gLO_sBM_c05_d14_mLO5_ch02 (ключ датасета gLO_sBM_cAll_d14_mLO5_ch02), сменная аргументом --seq.

Проба проверяет весь путь насквозь: эталон из датасета, призраки, живой сенсор, приблизительная помоментная оценка. Это одноразовый прототип-инструмент `tools/player_trial`, а не старт приложения Player: его сценарии ([index.md](index.md)) ещё ждут подтверждения, контракты core-спеков не заполнены. Наработки (канонический вид, сравнение, отрисовка призраков) переиспользуются дальше, пробная метрика заменяется контрактом скоринга без изменения остального.

Открытые вопросы сняты владельцем 2026-11-21: трекер — все три режима с переключением; метрика — близость костей, бегущий процент и счётчик грубых ошибок; последовательность — имя указывает владелец.

## Scenarios

**S1.** Проба работает на одной последовательности датасета AIST++: видео идёт в окне со своей звуковой дорожкой, часы видео это часы пробы.

**S2.** Экран делится на две части: видео эталонного танцора и сцена с призраками. Вспомогательная информация ограничена оценкой из S5 (системный спек S1-S2, упрощение пробы).

**S3.** Сцена показывает двух призраков: эталон-призрак по канонической позе эталона, приведённый к пропорциям пользователя по длинам костей, и призрак пользователя по живому сенсору. Оба движутся синхронно с видео.

**S4.** Отклонение формы движения подсвечивается цветом на призраке пользователя сразу, в момент движения; интенсивность плавная, растёт с отклонением, дискретных оценок «верно/неверно» нет (системный спек S3; пробная кривая нормировки, параметры в реестре оценок).

**S5.** Оценка успешности приблизительная: бегущий процент совпадения за последние секунды, накопленный итог и счётчик грубых ошибок на экране, суммарный итог по окончании трека. Порог грубой ошибки пробный, задаётся наугад до натанцовки и живёт в реестре оценок; оценка не является контрактом скоринга и заменяется им.

**S6.** Сравнение не зависит от роста, пропорций и положения в комнате: направления костей в системе координат торса, перемещение корня в долях длины ноги (canonical-pose S1, S9; инварианты S18, S19 выполняются построением).

**S7.** Перед сравнением ищется один общий временной сдвиг пользователя в узком окне; сдвиг меняется плавно, ограниченной скоростью (скоринг S6, S7, упрощённый поиск).

**S8.** Эталон, сравненный сам с собой, даёт максимум оценки и нулевое отклонение (инвариант S14 как минимальная проверка метрики пробы; остальные инварианты на пробе не проверяются).

**S9.** Недостоверные суставы (плохое отслеживание) исключаются из сравнения и не подсвечиваются; при полной потере человека показывается состояние «не вижу», видео и музыка продолжаются.

**S10.** Вычислительная нагрузка не останавливает видео и звук; призрак и оценка могут временно отключаться (системный спек S13).

**S11.** Живой источник позы: три режима трекера с переключением на живом окне, как в sensor_view (Kinect SDK, Nuitrack нативный, Nuitrack AI); в кадре один человек, ближайший к сенсору. Эталон строится утилитой импорта в `tools/aist_import` (Python, разрешённая зона) из сглаженных 3D-точек COCO-17 на равномерной сетке 60 fps; суставы chest, neck, head строятся приближённо из доступных точек.

**S12.** Управление воспроизведением доступно кнопками окна: плей/пауза, рестарт с нуля, запуск попытки; горячие клавиши Space и R дублируют кнопки (добавлено по живому прогону владельца 2026-11-22: «видео проигралось всего один раз, при этом я не могу его запустить заново; нужны кнопки для управления»).

**S13.** Ракурс видео эталона переключается в окне между камерами датасета, доступными для последовательности (9 ракурсов AIST++), позиция воспроизведения при переключении сохраняется и видео продолжается с того же места. Кнопки выбора ракурса расположены по схеме камер кольцом вокруг танцора, чтобы одним кликом было понятно, какой ракурс получится; азимуты берутся из калибровки камер датасета (c01 около +180, c02 +135, c03 +92, c04 +42, c06 -45, c07 -89, c08 -135, c05 фронтальный 0; при реализации E4 реальные азимуты заменяли первоначальное допущение о равномерных 40 градусах — точнее к видео) (уточнение владельца 2026-11-22: «расположим их как если бы это были прямо камеры со своих ракурсов, и можно было одним кликом понять, какой будет; при переключении ракурса тайминг видео должен оставаться тот же что был и продолжаться дальше»). Просмотр с любого ракурса не требует сенсора и оценки.

**S14.** Кнопка «Попытка» перед стартом даёт паузу с обратным отсчётом на экране, 3-5 секунд по выбору в окне, чтобы отойти от ноутбука и встать в стартовую позу; по концу отсчёта видео и оценка начинаются с нуля (владелец, 2026-11-22: «старт с паузой на 3-5 секунд чтобы отойти от ноутбука и встать в стартовую позу»).

**S15.** Оба призрака стоят на одном полу: высота корня пользователя считается над оценкой пола, как у эталона. Пол живой сцены оценивается по лодыжкам отслеживаемого скелета (нижний перцентиль высот), оценка обновляется по мере движения (владелец, 2026-11-22: «эталонный призрак отображается от пола, а мой почему-то сильно ниже»).

**S16.** Проба и просмотр сцены это режимы одного окна приложения, а не отдельные инструменты: переключатель «Проба / Сцена сенсора». Режим сцены показывает скелеты всех людей в ракурсе сенсора (вид спереди и сверху), статистику потока и оценку пола, без видео и оценки движения; нужен, чтобы понять, что попадает в ракурс (владелец, 2026-11-22: «нужен режим просмотра сцены сенсора… это должны быть разные режимы одного приложения»).

**S17.** Скорость воспроизведения регулируется ползунком от 0.2 до 2.0: замедление для разбора движения, ускорение, когда движение освоено. Ползунок действует на видео, эталон-призрак и часы оценки одновременно (владелец, 2026-11-22: «смотреть запись и движения эталонного призрака с замедлением вплоть до 0.2, и наоборот ускорять до 2»).

**S18.** Сцена призраков трёхмерная: камера сцены поворачивается вслед выбранному ракурсу эталонного видео (азимут кнопки-камеры), оба призрака в одной 3D-сцене. Проекция решается матрицей поворота 3 на 3 и перспективным делением, графический движок не используется (решение старого спека экрана; владелец, 2026-11-22: «правая часть с призраками так же должна быть 3д, с соответствующим переключением ракурса при смене записи эталона»).

**S19.** Управление ракурсом и воспроизведением единое для эталонного видео и призраков: одна кнопка-камера одновременно меняет видео и камеру 3D-сцены, отдельных ракурсов у видео и призраков нет; плей/пауза, скорость, рестарт и попытка управляют видео и призраками как одним целым по мастер-часам (владелец, 2026-11-22: «фактически управление ракурсом и прочим для эталонного видео и призраков должно быть единым»).

**S20.** Перед и зад призраков читаются со всех ракурсов, включая повороты, цветовой разметкой поверхности капсул: каждая капсула рисуется слоями со смещением в 3D — передняя сторона тёплым/ярким оттенком, задняя холодным/тёмным; при повороте в профиль слои сходятся на ребро и читается бок. Торс — те же передняя и задняя панели (грудная ярче). На голове бейсболка с козырьком вперёд (козырёк маркирует перед), под призраком стрелка направления на полу (владелец, 2026-11-22: «на груди-спине тоже что-то должно быть; всю переднюю-заднюю плоскость капсул от боковых отличать»; «шарики на капсуле головы кринжово, сделай бейсболку с козырьком вперёд»; «а на остальном скелете сделай цветовую разметку поверхности капсул да»). Повёрнутая вбок голова не ломает читаемость: тело читается панелями и полосами (владелец, 2026-11-22: «на груди-спине тоже что-то должно быть; в идеале всю переднюю-заднюю плоскость капсул от боковых отличать, чтобы повороты были проще»).

**S21.** Кадрирование укрупняет танцора: единый регулятор «Кадр» одновременно зумит видео эталона (с отрезанием боков сцены: стен и камер студии) и сцену призраков, умолчание увеличенное; принцип единого управления (S19) распространяется на кадр (владелец, 2026-11-22: «на эталонной съёмке процент человека в кадре едва ли кусочек… стоит отрезать части сцены по бокам чтобы укрупнить движения человека, а не белые стены и камеры, аналогично с призраками»). Авторазмер по калибровкам камер остаётся настоящему Player. Кадрирование следует за танцором: вертикальный якорь у низа кадра (пустая верхняя часть студии срезается первой), кадр следует за танцором автоматически: из 2D-кейпоинтов датасета (keypoints2d) импортёр выгружает пер-камерные треки корня и габарита танцора (bbox), плеер автоматически выбирает зум под габарит с запасом и центрирует окно по обеим осям; слайдер «Кадр» — множитель поверх авто (умолчание x1.0) (владелец, 2026-11-22: «почему у танцора слева теперь ноги срезаны, и верх всё ещё половина белого?»; центр-якорь режет симметрично и мимо: танцор в AIST-кадре смещён у боковых камер).

**S22.** Пауза — режим подгонки позы: видео и эталон-призрак застывают, призрак пользователя остаётся живым, подсветка отклонений работает против застывшего эталона с фиксированным на момент паузы сдвигом; HUD в паузе показывает мгновенный процент совпадения позы (по кривой мёртвой зоны и насыщения), чтобы доводить положение тела до максимума (владелец, 2026-11-22: «остановка сцены на паузу на случай если мне непонятно движение и я хочу добиться правильного положения своего тела, подгоняя под остановленное эталонное»).

### Out of scope

- Карта глубины в режиме сцены пробы (скелеты достаточно; глубина добавится при необходимости).
- Полный скоринг по инвариантам S15-S21 и его фикстуры: остаются за контрактом скоринга.
- SMPL-путь импорта эталона (основной для Studio по canonical-pose S12), подгонка SMPL по ключевым точкам.
- Профили пользователей, бандлы треков, производный кеш, Studio.
- Режим непрерывного повтора (системный S16), возврат между циклами, реплей после трека, отчёт с разбором ошибок.
- Много людей в кадре, многосенсорность.
- Нарезка на движения, словарь элементов, задержка запуска и калибровка.
- Сохранение результатов пробы, кроме уже существующей записи сессии захвата.

## Варианты

### Вариант A: эталон из keypoints3d_optim

Сглаженные 3D-точки COCO-17 уже есть на каждую последовательность (1408 файлов), шум после сглажения в среднем 0.71 см (docs/aist-format-findings.md). Дёшево, быстро, шума достаточно для пробы. Минус: chest, neck, head строятся приближённо, точки COCO не совсем суставы.

### Вариант B: эталон из SMPL FK

Вращения smpl_poses есть на все 411 последовательностей, формула прямой кинематики проверена (docs/aist-format-findings.md, среднее расхождение с точками около 3 см). Точнее по определению суставов и соответствует canonical-pose S12 как основному пути. Минус: нужны файлы модели SMPL и заметно больше кода.

**Выбор:** A для пробы (скорость и простота, шум приемлем для приблизительной оценки); B остаётся основным путём импорта для Studio.

## Contract

### Новое публичное API

C# (`src/DanceLab.Core`, новый namespace `DanceLab.Core.Canonical`):

- `CanonicalFrame`: восемь направлений костей единичной длины в системе торса (`uArmL, uArmR, lArmL, lArmR, thighL, thighR, shinL, shinR`, по три числа), `TorsoLeanRad, TorsoTurnRad, HeadTiltRad`, корень `RootForward, RootSide, RootHeight` в долях длины ноги, `HeadingRad`, `TSec`.
- `CanonicalTrack`: `Fps`, `LegLengthM`, кадры; `CanonicalFrame Sample(double tSec)` с линейной интерполяцией.
- `TrialComparer.Compare(CanonicalFrame reference, CanonicalFrame user)` → `TrialComparison { BoneDeviationRad[8], MeanDeviationRad, Coverage }`; Coverage доля костей, участвующих в сравнении (валидные у пользователя).
- `TrialScorer` (stateful): хранит лучший временной сдвиг (окно E84, скорость изменения E85); `Update(double tSec, CanonicalFrame user)` → `TrialScore { Running01, Total01, Errors, Coverage, ShiftSec }`.
- `Canonicalizer.ToCanonical(ReconstructedPose pose, IReadOnlyDictionary<string, LimbLengths> boneLengths, double legLengthM, double floorYm = 0)` → `CanonicalFrame`: имена суставов от реконструкции, торс-фрейм по canonical-pose S7; высота корня считается от `floorYm` (оценка пола живой сцены, S15).

Python (`tools/aist_import/canonical_export.py`):

- CLI: `--seq <имя с cAll> [--src data/aist/extracted/keypoints3d] [--out data/derived/trial]`.
- Выход: `<seq>.canonical.json` по схеме ниже; в stdout контрольные числа: количество кадров, медиана длины ноги в см, количество кадров с NaN.

WPF (`tools/player_trial`, net48, WinExe, код-стиль sensor_view без XAML):

- Аргументы: `--seq <имя>` (по умолчанию эталон пробы), `--tracker kinect|nuitrack|nuitrack-native|nuitrack-ai`, `--mode probe|scene` (стартовый режим), `--camera cXX` (стартовый ракурс, S13), `--zoom <1.0-3.0>` (стартовый кадр, S21), `--shot <png> [--shot-after сек]` (визуальная приёмка), `--no-sensor` (прогон эталона без сенсора).
- Окно: слева видео (MediaElement, звук из дорожки видео), справа сцена с двумя призраками и HUD: бегущий процент, накопленный итог, счётчик грубых ошибок, покрытие, «не вижу».

### Изменения существующего API

Нет. Core, Capture и sensor_view не меняются; рендер призраков копируется из `tools/sensor_view/SkeletonCanvas.cs` в player_trial с адаптацией (два призрака, цвет кости по отклонению). Вынос в общую библиотеку делается при старте настоящего Player, не в пробе.

### Интеграция

- Живые источники позы: как в sensor_view (`KinectPoseSource`, `NuitrackPoseSource("viewer", ...)`), переключение трекера комбобоксом; реконструкция `MultiUserReconstructor`, в пробе берётся ближайший к сенсору пользователь.
- Мастер-часы: позиция `MediaElement`; кадры сенсора приходят со своими таймстампами и сэмплируют эталон `CanonicalTrack.Sample` по часам видео.
- Длины костей пользователя для эталон-призрака и нормировки корня: медиана по первым секундам живого скелета, до этого призрак эталона в длинах эталона.
- Запись сессии: существующий `LiveRecorder` по кнопке, без изменений.

### Типы / схемы данных

`<seq>.canonical.json` (formatVersion 1, UTF-8, углы в радианах):

```json
{
  "formatVersion": 1,
  "sequence": "gLO_sBM_cAll_d14_mLO5_ch02",
  "video": "gLO_sBM_c05_d14_mLO5_ch02.mp4",
  "fps": 60,
  "frameCount": 720,
  "legLengthCm": 71.3,
  "frames": [
    {
      "t": 0.0,
      "bones": { "uArmL": [0,0,1], "uArmR": [0,0,1], "lArmL": [0,0,1], "lArmR": [0,0,1],
                  "thighL": [0,1,0], "thighR": [0,1,0], "shinL": [0,1,0], "shinR": [0,1,0] },
      "torso": { "lean": 0.0, "turn": 0.0 },
      "head": { "tilt": 0.0 },
      "root": { "forward": 0.0, "side": 0.0, "height": 0.9, "heading": 0.0 }
    }
  ]
}
```

Построение из COCO-17 (импортёр): root = середина бёдер; neck = середина плеч (приближение пробы); chest = середина root-neck; head = середина ушей либо нос; система торса и единицы по canonical-pose S7 и S9; сглаженные точки `keypoints3d_optim`; кадры с NaN пропускаются с фиксацией в stdout.

Отрисовка эталон-призрака: прямая кинематика по направлениям костей с длинами костей пользователя, старт от root, heading задаёт направление взгляда.
