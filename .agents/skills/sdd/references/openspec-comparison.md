# Сравнение с OpenSpec

[OpenSpec](https://github.com/Fission-AI/openspec) — популярный фреймворк для SDD (64k stars, MIT, активно развивается). Прежде чем делать своё — мы изучили его внимательно.

## Что OpenSpec делает хорошо

- CLI-автоматизация: `/opsx:propose`, `/opsx:apply`, `/opsx:archive` автоматически создают папки, мержат дельты обратно в спеки
- Explore-фаза (`/opsx:explore`) — агент исследует кодовую базу до написания спека
- Verify-фаза (`/opsx:verify`) — проверка что реализация соответствует артефактам
- Stores — планирование в отдельном репо, кросс-репо фичи
- 30+ интеграций с разными AI-инструментами
- Кастомные схемы с зависимостями между артефактами

Это реальные преимущества. Часть из них мы перенесли в свой процесс напрямую (см. «Что взяли»).

## Почему не OpenSpec

Большинство наших требований технически закрываются через кастомную схему: иерархия абстракций — конвенция в `openspec/specs/`, human-gates — через `instruction` в схеме (community schema `anvil` уже так делает), формат Scenarios/Contract — через `rules.specs` и шаблоны. Мы проверили это на ветке `try-sdd-openspec`.

Реальный блокер — структура монорепо. Подробности в разделе ниже.

## Что мы потеряли

**Автоматический archive/merge.** Слияние дельты обратно в основные спеки — у OpenSpec это одна команда. У нас это делается вручную.

**Stores.** Кросс-репо планирование OpenSpec решает структурно. У нас этого нет — каждое репо ведёт спеки самостоятельно.

## Что взяли из OpenSpec

**Explore-фаза.** Шаг 1 нашего процесса — агент сначала читает существующие спеки и код, раскладывает варианты, и только потом уточняет с человеком. Прямое заимствование идеи `/opsx:explore`.

**Verify-шаг.** Шаг 7 включает явную проверку: каждый пункт контракта присутствует в коде, ничего из Out of scope не просочилось. Идея `/opsx:verify`.

**Tasks как чеклист внутри спека.** В OpenSpec это отдельный `tasks.md`. Мы держим его внутри спека — появляется при `realisation`, удаляется при `done`.

## Блокер при попытке перейти на OpenSpec (ветка [`try-sdd-openspec`](https://gitlab.tcsbank.ru/formbuilder/ai/-/tree/try-sdd-openspec))

Была предпринята попытка натянуть наш SDD-процесс на OpenSpec как базовый инструмент — кастомная схема (`schema.yaml` + шаблоны) с нашим форматом Scenarios/Contract, двумя human-gates и иерархией абстракций. Попытка остановилась на структуре монорепо.

**Проблема:** в монорепо с большим количеством блоков нужно одновременно:

1. **Co-located спеки** — `packages/block-name/specs/` рядом с кодом блока
2. **Связный контекст** — изменения в системных спеках каскадируют в блочные и наоборот; 50–75% работы в блочных спеках

OpenSpec поддерживает только два сценария:

- Единый `openspec/` в корне — нет co-location
- Отдельный `openspec/` на каждый блок (`openspec init packages/block-a`) — нет связного контекста между блоками и корнем, нет кросс-ссылок через CLI, высокие накладные расходы на поддержку N блоков

Ни один вариант не даёт одновременно co-location и связный контекст. Stores в OpenSpec предназначены для кросс-репо сценариев, не для внутримонорепного co-location.
