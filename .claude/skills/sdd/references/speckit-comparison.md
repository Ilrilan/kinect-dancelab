# Сравнение с GitHub Spec Kit

[Spec Kit](https://github.com/github/spec-kit) — open-source toolkit от GitHub для Spec-Driven Development с AI-агентами (28K+ stars, MIT). Мы используем другую модель; вот почему.

## Модель Spec Kit

**Feature-branch-centric.** Каждая фича получает ветку и папку `specs/[branch-name]/` с набором артефактов: `spec.md`, `plan.md`, `data-model.md`, `contracts/`, `research.md`, `tasks.md`. После мержа ветка исчезает — спек не живёт как постоянный документ.

Процесс автоматизирован через CLI-команды: `/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`. Явных "стоп, жди подтверждения человека" нет — процесс ориентирован на скорость генерации.

Фокус: _ускорить кодогенерацию через структурированный промпт-пайплайн_.

## Наша модель

**System-centric.** Спеки — постоянные документы организованные по доменам, а не по фичам. Фича описывается в домене которому принадлежит, и остаётся там после реализации. Два обязательных гейта с подтверждением человека (scenarios → realisation).

Фокус: _спек как долгоживущий источник правды о намерении_.

## Почему не Spec Kit

**Спеки как временные артефакты.** В Spec Kit спек живёт в ветке фичи и архивируется после мержа. Агент, открывая репо через месяц, не видит системного знания — только историю git. У нас `specs/` отражает текущее состояние системы в любой момент.

**Нет иерархии абстракций.** Spec Kit не имеет понятия system → domain → feature. Все спеки плоские (по фичам). Нет parent/child, нет drill-down, нет домен-индексов. У нас агент может прочитать `system.md` и понять контекст задачи прежде чем идти в конкретную фичу.

**Нет обязательных human-gates.** Spec Kit ориентирован на автономную генерацию. Мы требуем явного подтверждения человека дважды — после сценариев и после контракта. Это принципиально: реализация не начинается без одобренного контракта.

**Множество файлов на фичу.** 6 артефактов на одну фичу (spec, plan, data-model, contracts, tasks, research) — административная нагрузка для небольших и средних изменений. Мы держим всё в одном файле, drill-down только когда действительно нужен.

**CLI-зависимость.** Spec Kit требует установки `specify-cli`. Наш процесс — чистый markdown, работает с любым агентом без дополнительного инструментария.

## Что стоит взять из Spec Kit

**`[NEEDS CLARIFICATION: вопрос]`** — маркировать неоднозначности прямо в тексте спека, не вынося в отдельную секцию. Дополняет секцию "Открытые вопросы": та — для блокирующих вопросов, маркер — для точечных неясностей внутри уже написанных сценариев и контракта.

**`[P]` для параллельных тасков** — в секции Tasks отмечать независимые задачи которые можно выполнять одновременно.
